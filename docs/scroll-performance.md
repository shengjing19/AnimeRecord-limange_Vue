# 滚动与封面性能优化（v1.1.1）

2026-11-12。本次保留 Vue 3 和 Electron，在现有项目中优化。没有证据表明 Vue 已达到性能上限，因此没有创建另一套重构工程。

## 定位到的开销

- 虚拟列表原本已限制 DOM 数量，但每次滚动都修改响应式 `scrollTop`，生成新可见数组，使列表反复执行渲染与差异比较。
- 卡片离开虚拟窗口后被回收，回来时重新排队加载。HTTP 缓存并不保证原图仍处于已解码状态；数十张大图的重新解码和栅格化仍然有成本。
- 除 TMDB original 地址外，许多列表封面仍使用原图。之前测试使用 21 张循环复用的图片，不能充分覆盖每条记录各自拥有大图的场景。

## 已实现的改动

1. **跨行才更新 Vue**：滚动位置放在非响应式变量中，二分计算行区间。区间不变就直接返回；重叠行使用 `v-memo`，保留现有卡片。滚动监听仍是被动监听，沿用浏览器原生滚动。
2. **后台生成封面缩略图**：最多两个 Worker 执行下载、解码、缩放和 JPEG 编码，列表使用 384px 封面，高 DPI 使用 512px。缩放使用 CPU 小画布，避免编码前的 GPU 回读。原始详情图不变。
3. **有界缩略图缓存**：只缓存压缩 Blob，不保留原图或 ImageBitmap；最多 256 项、16 MiB 编码内容。正在显示的图片受引用保护，释放后再收敛到预算。缓存键包含后端地址，避免切换服务器后串图。Chromium 自己管理的解码缓存和 GPU 纹理不包含在这个 16 MiB 预算中。
4. **可见图片优先**：一个滚动根对应一个 IntersectionObserver；先处理距离可视区域中心近的图片。前台最多四个加载槽，离屏回收时取消排队和后台任务。坏图、超时、Worker 不可用或图床不支持 CORS 时回退到普通图片加载。
5. **控制重绘范围**：隔离卡片内部绘制，固定壁纸单独合成，不为每张卡片创建 GPU 图层。

缩略图在当前进程内缓存，首次访问仍需下载原图，重启后会重新生成。若日志显示慢点主要来自网络，下一步应在 Newlimange 后端保存缩略图并返回独立地址，减少首次下载字节数；本次没有修改后端接口。

## 使用性能日志

打开 v1.1.1，在片库上下滚动，再进入 **设置 → 性能诊断 → 导出性能日志**。诊断默认开启，可关闭、清空或导出上次运行的快照。

- 滚动时及停止后的 160ms 内采样 requestAnimationFrame 间隔，静止时没有常驻逐帧循环。
- 记录 P95、最大帧间隔、超过估算刷新周期 1.5 倍的帧、超过 50ms 的帧，以及主线程长任务。
- 同时记录行范围检查与实际更新次数、图片队列、缓存命中、下载和缩图耗时。桌面版包含 Electron/Chromium 版本与 GPU 功能状态。
- 内存最多保留 120 个滚动窗口、180 条事件。停止滚动后保存有界快照到本机 `localStorage` 的 `limange_performance_last`，重启可导出上次日志。不向服务器上传，不记录账户、令牌、作品标题、服务器地址或图片 URL。

P95 持续超过 33ms、频繁出现 50ms 以上帧间隔，说明有明显延迟。120/144Hz 设备的目标帧间隔更低，应同时查看估算周期和慢帧比例。RAF 反映主线程调度间隔，不能代替 GPU 呈现追踪；纯 GPU 卡顿可能需要结合系统图形工具分析。

## 复现与验证

```sh
npm test
npm run build
npm run test:covers
npm run test:ui
npm run test:desktop
npm run test:scroll
```

`test:scroll` 使用生产构建、Edge 无头模式、1440×900、240 条记录。21 张 1600px 宽的测试图片通过每条记录独立的 URL 加载，执行冷下滑、返回、再次下滑，各 240 帧，每帧移动 32px。包括可见图片空白比例验收，不能用不显示图片换取更好的帧率。额外执行真实鼠标滚轮输入并确认视口图片最终全部显示。

改动前的生产构建保存在本机 `.temp/scroll-before-dist` 时，可执行 `node scripts/scroll-profile.cjs --compare`。该目录被 Git 忽略，新克隆中需自行准备对应旧构建。结果在 `.temp/qa/scroll-performance.json`，截图、诊断日志也在 `.temp/qa/`。通过 `PERF_CPU_RATE` 可另外测试 CPU 降速，但不同运行条件不可直接混比。

像素体积指标是“已挂载图片 naturalWidth × naturalHeight × 4”的估算，用来对比原图与缩略图规模，**不是进程实际内存或 GPU 显存读数**。无头浏览器测量不保证用户设备在所有窗口尺寸、刷新率和网络条件下都达到相同表现。

本机一次独立顺序对比（未与其他测试并行，未进行 CPU 降速）：

| 指标 | 改动前 | v1.1.1 |
| --- | ---: | ---: |
| 返回上滑的主线程任务总耗时 | 718.8 ms | 500.3 ms（减少 30.4%） |
| 再次下滑的主线程任务总耗时 | 705.2 ms | 460.0 ms（减少 34.8%） |
| 三段测试超过 33.4ms 的帧 | 3 | 0 |
| P95 帧间隔范围 | 17.0–17.1 ms | 16.9–17.1 ms |
| 返回/再次下滑的可见封面空白比例 | 0% / 0% | 0% / 0% |
| 已挂载图片峰值像素体积估算 | 665.11 MiB | 38.30 MiB |
| 首批六张封面就绪 | 303 ms | 426 ms |
| 冷下滑主线程任务总耗时 | 855.0 ms | 954.9 ms |
| 冷下滑可见封面空白比例 | 0% | 1.6% |

结果主要改善了已看过封面的往返滚动与大图规模，不能声称所有指标都提高：首次缩图增加约 123ms 就绪时间，冷滚动也多出一些处理成本。两版 P95 都接近本次浏览器的 60Hz 周期。诊断记录中 725 次范围检查只有 135 次实际窗口更新，缓存命中 254 次，编码缓存约 14 MiB。

另外通过了真实 Electron 的 `app://` 协议、Worker 缩略图及安全回归；测试机 GPU 合成与栅格化均为 enabled。191 条记录的快速首尾跳转、错误图片、无 CORS 图床直载回退、队列清空、日志开关/导出/重启恢复均通过独立浏览器用例。

## 是否需要迁移

当前不需要更换框架或语言。优先观察真实设备日志，补后端缩略图，并检查 GPU 合成状态。

只有在图片、网络、更新频率都排除后，仍能稳定证明 Chromium 渲染路径无法满足目标设备时，才值得先做隔离原型并对比：

| 方案 | 适用情况 | 成本与限制 |
| --- | --- | --- |
| C# + WinUI 3 | 只面向 Windows，希望使用原生列表虚拟化与合成 | 需要重做界面、状态和交互；可复用后端 HTTP API |
| C++ + Qt Quick | 需要跨平台的原生场景图渲染 | 开发和部署复杂度较高，仍需正确管理图片尺寸与缓存 |
| Rust + Tauri + 现有 Vue | 主要目标是缩小安装包、替换桌面宿主 | 仍用 WebView 绘制 Vue 页面，不应把它当作解决滚动卡顿的保证 |

如果将来满足迁移条件，再在根目录创建独立原型目录，使用同一测试数据、窗口尺寸、滚动路径验证后决定是否重写。仅改成 TypeScript、React 或另一种语言不会自动消除图片和绘制开销。
